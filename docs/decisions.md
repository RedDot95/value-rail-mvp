# Architekturentscheidungen (Delivery 1)

| ID | Entscheidung | Begründung |
|----|--------------|------------|
| D-01 | **Modularer Monolith** in Python (`src/value_rail/*`), ein Prozess pro Rolle (Web, Worker, CLI) auf derselben DB | Bauauftrag; minimaler Betriebsaufwand, klare Modulgrenzen für spätere Extraktion |
| D-02 | **Decimal überall für Geld**; Floats werden in Pydantic-Modellen (`BeforeValidator`) und DB-Typ (`DecimalText`) aktiv abgewiesen; fester Decimal-Kontext (prec 28, ROUND_HALF_EVEN) | Exakte, reproduzierbare Beträge; SQLite-NUMERIC würde über float runden → Decimal als TEXT gespeichert |
| D-03 | **UTC intern**, `UTCDateTime` speichert ISO-8601 mit `+00:00`, naive Datetimes werden abgelehnt; Anzeige in Europe/Berlin (Jinja-Filter `berlin`) | Bauauftrag; keine DST-Fehler |
| D-04 | **Unveränderliche Snapshots**: products, offer_snapshots, evidence, rule_versions, quotes, route_evaluations, execution_results. Doppelt abgesichert: ORM-`before_flush`-Guard **und** SQLite-Trigger (`RAISE(ABORT)`) aus der Migration. Korrekturen = neue Zeile mit `version+1`, `supersedes_id` | Audit-Fähigkeit; auch Roh-SQL kann nichts überschreiben |
| D-05 | **"unknown" statt null** für fehlende Pflichtinformationen (Preis, Währung, Mengen, Zeitstempel, Restkapazität, Ursache) | Bauauftrag; "unbekannt" ist eine Aussage, null wäre mehrdeutig |
| D-06 | **Drei getrennte Mengenfelder** (`advertised_quantity`, `checkout_confirmed_quantity`, `purchased_quantity`), jeweils mit `observed_at` + `scope` | Angezeigt ≠ kaufbar ≠ gekauft; Fall 3 (11 angezeigt / 3 gekauft) |
| D-07 | Zusätzlicher Status **`no_signal`** (neben price_find, verified_route, blocked, expired, executed, failed) | Jede Bewertung wird für Audit/Replay gespeichert, auch wenn keine Schwelle erreicht ist (z. B. Direktpreis 56 € > Nennwert 50 €). `no_signal` wird nie alarmiert und nicht als Fund angezeigt. Bitte im Review bestätigen. |
| D-08 | **Statuspräzedenz**: harter Block (Identität, unbekannte Währung, unbekannte Pflichtgebühr, nur Aggregator-Preis) → `blocked`; vollständige frische Route über Schwellen → `verified_route` (unter Schwelle → `no_signal`); vollständige Route mit veraltetem Quote oder veraltetes Preisbasis-Angebot → `expired`; belegter Nominalrabatt ≥ Schwelle → `price_find`; sonst `no_signal` | Konservativ: ein Block schlägt jede positive Aussage |
| D-09 | **Profit/Edge nur bei vollständiger, unblockierter Route** berechnet; Preisfund/Blockiert zeigen Profit = "unbekannt" | Keine behaupteten EUR-Gewinne ohne belegten Exit (Fall 2) |
| D-10 | **Bewertete Menge q = min(checkout-bestätigte Menge, belegte Exit-Tiefe)**; acquisition_cost(q) und net_exit(q) werden aus Stückpreis + Gebühren berechnet (fix/Order, fix/Stück, Prozent) | Fall 9; Gebühren skalieren korrekt; Monotonie (Fall 10) |
| D-11 | Gebühr mit `included_in_quote=true` wird nur als 0,00-Zeile dokumentiert, nie addiert; Angebot mit `price_includes_fees=true` addiert gelistete Gebühren nicht erneut | Keine Doppelgebühr (Fall 11) |
| D-12 | **Aggregatoren sind `discovery_only`**: ihre Preise sind nie Preisbasis; nur identische Direktangebote (alle 6 Identitätsfelder gleich, kein Feld "unknown") zählen. Nur-Aggregator → `blocked` | Fall 1 |
| D-13 | **Produktidentität** = Nennwert + Währung + Region + Variante + Seller + Einlöseprogramm; **Asset-Identität** = Chain + Contract (Ticker irrelevant, DB-Unique-Constraint) | Fälle 7, 8 |
| D-14 | **"$" allein ⇒ Währung unknown** (auch ¥, kr); nur eindeutige Marker (€, EUR, US$, USD, £ …) setzen eine Währung. Unbekannte Währung blockiert; bekannte Fremdwährung ohne FX-Kurs blockiert ebenfalls | Fall 6 |
| D-15 | **Replay**: `RouteInputs` enthält alles inkl. Bewertungszeitpunkt; gespeichert werden kanonisches Inputs-JSON, Inputs-Hash, Output-JSON, `rule_version_id`, `engine_version`. Regelversionen sind unveränderlich und über `valid_from` aktiv | Fall 16; exakte Reproduktion solange `engine_version` gleich ist (Code-Änderungen an der Engine erhöhen die Version) |
| D-16 | **Transaktionale Outbox**: Snapshot, Quotes, Evidenz, Bewertung **und** Alert-Zeile in **einer** Transaktion pro Route. Connector-Daten werden vorher vollständig geholt (keine offene Transaktion während I/O) | Fall 14; kein Alert ohne Bewertung und umgekehrt |
| D-17 | **Stabile Event-IDs**: `sha256(route_key, fingerprint, previous_event_id)[:32]`, unique in der Outbox. Fingerprint = Status, all-in-Stückpreis, verfügbare/angezeigte Menge, Preisbasis-Typ, Regel-Label | Fall 12 (identischer Rescan erzeugt nichts), A→B→A erzeugt dennoch ein neues Event |
| D-18 | **Materialität**: neues Event bei Statuswechsel, Preisänderung ≥ `material_price_change_pct` (2 %) ggü. letztem Alert, Restock (0/unknown → >0 oder +N). Mengenrückgang erzeugt kein Event | Fall 13; konfigurierbar in `config/default.toml` |
| D-19 | **At-least-once-Zustellung** mit begrenzten Retries (`max_attempts`=5, lineares Backoff), danach `dead`. **Duplikate sind möglich**, wenn der Sink zugestellt hat, der Prozess aber vor dem `sent`-Commit abstürzt; Konsumenten deduplizieren über `event_id` | Bauauftrag "mögliche Duplikate dokumentieren" |
| D-20 | **Störung ≠ keine Deals**: `SourceUnavailable` markiert Quelle `down`, Scan `degraded`, betroffene Route wird **nicht** neu bewertet; UI markiert Altdaten als veraltet | Fall 15 |
| D-21 | **SSR statt SPA**: FastAPI + Jinja2, ein CSS-Block inline, keine Build-Kette; Basic-Auth optional | Bauauftrag; iPhone-tauglich ohne Frontend-Build |
| D-22 | **SQLite** mit WAL, `synchronous=FULL`, Foreign Keys an; Schema ausschließlich über Alembic (Autogenerate-Check im Test: Modelle == Migration) | Single-Node-Prototyp; Migrationen versioniert |
| D-23 | Versionen gepinnt am 05.10.2026 gegen aktuelle PyPI-Releases: FastAPI 0.142.2, Starlette 1.7 (transitiv), Uvicorn 0.54.0, SQLAlchemy 2.1.3, Alembic 1.20.0, Pydantic 2.13.5, pydantic-settings 2.15.0, Jinja2 3.1.6, Typer 0.27.2, pytest 9.1.1, httpx2 2.13.1 (Starlette-1.x-TestClient) | Bauauftrag "current supported versions" |
